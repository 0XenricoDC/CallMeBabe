<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller speech → tool args | date/time/covers/name/phone come from STT — untrusted |
| handler → SQLite | tenant_id (from fm.state session context) + slot fields written to reservations |
| handler → Google Calendar | calendar_id resolved from TenantConfig, event body includes caller PII |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-04 | Spoofing/Repudiation | hallucinated confirmation | mitigate | Tool-result gating: end node reachable only when create_event returns a real id; confirmation text lives solely in build_end_node (test_confirm_only_after_event_id, test_no_confirm_on_calendar_failure). |
| T-02-05 | Tampering | double-booking race | mitigate | BEGIN IMMEDIATE check-and-insert in try_reserve_slot; verified by test_concurrent_booking (SC3). |
| T-02-06 | Elevation of Privilege | cross-tenant calendar write | mitigate | calendar_id resolved from TenantConfig (DB), never from caller-supplied tool args; tenant_id from fm.state session context (T-03). |
| T-02-07 | Information Disclosure | PII (phone/name) in logs | mitigate | except clauses in handle_confirm_booking never log args/customer; credential path never logged. |
| T-02-08 | Denial of Service | blocking Google call stalls event loop | mitigate | create_event uses run_in_executor (Pitfall 4) so VAD/barge-in keep running during the write. |
| T-02-PARTIAL | Repudiation/Consistency | calendar write succeeds but confirm_reservation DB write fails | accept | A stale Google event may exist with no 'confermata' row; recovery rationale: the bozza row persists, the handler speaks NO confirm (stays in booking node), and re-confirm is idempotent (UPDATE existing bozza by slot/name). Documented by test_db_confirm_failure_after_calendar_write (W4). |
</threat_model>
