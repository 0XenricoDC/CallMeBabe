<objective>
Close UAT gaps SC3 (blocker) and SC4: with an invalid DEEPGRAM_API_KEY the bot returned NO response and logged repeating `401, body: Websocket initialized with invalid credentials.` — `ServiceSwitcherStrategyFailover` never switched to faster-whisper, never spoke the courtesy phrase, and `ErrorFallbackObserver` never escalated. Both gaps share ONE root cause.

ROOT CAUSE (verified against the installed pipecat 1.4.0 source):
- `DeepgramSTTService._connection_handler()` (services/deepgram/stt.py:629-657) opens the WebSocket inside `async with self._client.listen.v1.connect(...)`. A connect-time 401 raises BEFORE the `EventType.ERROR` handler is registered, so it is caught by the broad `except Exception as e: logger.warning("Connection lost, will retry")` and the loop retries forever. This path NEVER calls `push_error`, so NO ErrorFrame is produced.
- `ServiceSwitcher.push_frame()` (pipeline/service_switcher.py:318-320) only calls `strategy.handle_error()` for a NON-FATAL `ErrorFrame` whose `frame.processor == active_service`. With no ErrorFrame, failover never fires.
- `ErrorFallbackObserver.on_push_frame` likewise only acts on `ErrorFrame`s; with none produced, escalation never fires.
- `FrameProcessor.push_error()` (processors/frame_processor.py:642 → push_error_frame:678) creates an `ErrorFrame`, sets `error.processor = self` if unset, defaults `fatal=False`, and pushes UPSTREAM — i.e. calling `push_error` from the Deepgram service is exactly what the switcher and observer need.

FIX (three coordinated pieces):
1. `FailoverDeepgramSTTService(DeepgramSTTService)`: a connection-health monitor task that, while the connection is persistently NOT ready (covers connect-time 401/auth and mid-call drops), surfaces the failure via `self.push_error(..., fatal=False)` on an interval — so the switcher fails over (SC3) and keeps re-failing-over while a service stays dead. The existing `_on_error` already covers post-connect transcription/runtime errors.
2. `LazyWhisperSTTService.run_stt`: wrap the lazy model load in try/except and YIELD a non-fatal `ErrorFrame` on failure (so `process_generator` surfaces it) instead of letting the exception propagate — makes the whisper leg of SC4 ("both STT down") surface symmetrically.
3. SC4 escalation driven by repeated failover: count `on_service_switched` events; the first switch speaks the SC3 courtesy phrase (call continues), and when switches reach `_ESCALATION_THRESHOLD` (reuse the D-13 value = 3, meaning all STT services are flapping/dead) escalate once — set `flow_manager.state['outcome']='fallito'`, queue the transfer courtesy phrase + `EndWorkerFrame`. A single shared escalation guard (in `flow_manager.state`) coordinates with `ErrorFallbackObserver` so EndWorkerFrame fires exactly once across both mechanisms.

Purpose: the live forced-failure scenarios (SC3 = degrade to whisper and keep talking; SC4 = give up gracefully and transfer with outcome `fallito`, no long dead-air) actually work on the REAL error path — not just a simulated switch.
Output: updated `src/pipeline/stt_switcher.py`, `src/pipeline/build.py`, `src/pipeline/fallback.py`, `src/bot.py`; new real-error-path tests in `tests/test_stt_switcher.py` and `tests/test_fallback.py`.

ServiceSwitcher only triggers failover for an error from the ACTIVE service (service_switcher.py:318-320):
```python
if isinstance(frame, ErrorFrame) and not frame.fatal:
    if frame.processor and frame.processor == self.strategy.active_service:
        await self.strategy.handle_error(frame)
```
ServiceSwitcherStrategyFailover.handle_error round-robins to the next service and fires on_service_switched (service_switcher.py:182-205, 106-123).

push_error → push_error_frame (frame_processor.py:642, 678-698):
```python
async def push_error(self, error_msg, exception=None, fatal=False): ...   # builds ErrorFrame
async def push_error_frame(self, error: ErrorFrame):
    if not error.processor:
        error.processor = self            # <-- so frame.processor == this service
    ...
    await self.push_frame(error, FrameDirection.UPSTREAM)
```

DeepgramSTTService connection state (deepgram/stt.py):
```python
self._connection = None
self._connection_ready = asyncio.Event()   # set() AFTER connect succeeds (line 641); cleared on disconnect/retry (654, 619)
async def start(self, frame): await super().start(frame); await self._connect()
async def stop(self, frame):  await super().stop(frame);  await self._disconnect()
async def cancel(self, frame): await super().cancel(frame); await self._disconnect()
async def _on_error(self, error):           # post-connect errors ALREADY push_error
    await self.push_error(error_msg=f"{error}")
# _connection_handler() catches connect-time 401 in `except Exception` and retries WITHOUT push_error  ← the bug
```
On a 401 the `async with connect()` raises before `_connection_ready.set()`, so `_connection_ready` is NEVER set → the monitor can detect "persistently not ready".

LazyWhisperSTTService.run_stt currently lets a model-load exception propagate (stt_switcher.py:72-101). process_generator (services/ai_service.py:214-219) pushes YIELDED ErrorFrames via push_error_frame but does NOT catch a RAISED exception — so the load failure must be yielded as an ErrorFrame.

ErrorFallbackObserver escalation today (fallback.py): per-source retry slot (D-07) then per-source escalation counter, `_escalated` idempotency guard, `flow_manager.state['outcome']='fallito'` + TTSSpeakFrame + EndWorkerFrame at threshold. _ESCALATION_THRESHOLD = 3 (D-13 — keep the value).
